Fixedsign-25-1: Verifier verdict is decided by stale stack contentsDate not stated

This response concerns report sign-25-1: Verifier verdict is decided by stale stack contents.

Confirmation
We confirm the reported issue.
Root cause
The issue was caused by incomplete failure handling in the uncompressed verification path. For certain malformed signatures, the dimension-two isogeny chain could fail to produce a valid split codomain. Some of the relevant validity conditions were enforced only through assert statements, which are disabled in release builds when NDEBUG is defined. In addition, the failure status was not propagated explicitly to the verifier. As a result, verification could continue using a partially written codomain, and the final result could depend on residual stack contents from an earlier invocation.
Scope
This was a localized implementation issue and did not require any change to the signature scheme or signature encoding. The remediation was therefore relatively straightforward.
Remediation

We have fixed the reported issue by making following changes:

  • The dimension-two isogeny-chain computation now returns an explicit success or failure status.
  • Codomain data are produced and used only when the final splitting step succeeds.
  • The verifier checks the returned status and immediately rejects the signature if the computation fails.
  • Necessary basis-recovery and point-on-curve conditions are now enforced by unconditional runtime checks rather than debug-only assertions.
  • Malformed-input failure paths were revised so that verification never continues with incomplete intermediate values.
Outcome
After these changes, the verification result is determined solely by the public key, message, and signature. Valid signatures continue to verify correctly, while all-zero signatures, signatures for a different message, and malformed signatures that cause the isogeny-chain computation to fail are consistently rejected.

Fixedsign-25-3: Detached compact challenge enables one-query message-retargeting forgeriesDate not stated

This response concerns report sign-25-3: Detached compact challenge enables one-query message-retargeting forgeries.

Confirmation
We confirm the reported issue.
Root cause
In the original compact-signature implementation, the hash-derived challenge was transmitted and checked as a relatively independent signature field. However, the verifier did not sufficiently bind this value to the geometric relation between the reconstructed forward challenge isogeny and the encoded dual path. Consequently, the response and dual-path data could remain unchanged while the transmitted challenge was recomputed for a different message.
Scope
The remediation was conceptually clear, but it required coordinated changes to the compact signature format and to both signing and verification. It was therefore a moderate implementation change rather than a single additional input check.
Remediation

We have fixed the reported issue by making following changes:

  • The compact signature no longer carries the hash-derived challenge as a detached value.
  • During signing, the challenge kernel is constructed directly from the hash of the public key, message, and commitment curve using a canonical basis.
  • The compact encoding was updated to include the auxiliary information required to reconstruct the commitment curve and challenge relation during verification.
  • During verification, the commitment curve is reconstructed from the response and encoded dual-path information.
  • The verifier recomputes the challenge for the message being verified, constructs the corresponding forward challenge kernel, and checks that it is compatible with the recovered dual challenge path.
Outcome
These changes bind the message, commitment curve, forward challenge kernel, and dual challenge path within a single verification relation. Changing the message or replacing a challenge value without updating the associated geometric data no longer produces a valid signature.
