Fixedsign-25-1: Verifier verdict is decided by stale stack contentsDate not stated

This response concerns report sign-25-1: Verifier verdict is decided by stale stack contents.

Confirmation
We confirm the reported issue.
Root cause
The issue was caused by incomplete failure handling in the uncompressed verification path. For certain malformed signatures, the dimension-two isogeny chain could fail to produce a valid split codomain. Some of the relevant validity conditions were enforced only through assert statements, which are disabled in release builds when NDEBUG is defined. In addition, the failure status was not propagated explicitly to the verifier. As a result, verification could continue using a partially written codomain, and the final result could depend on residual stack contents from an earlier invocation.
Scope
This was a localized implementation issue and did not require any change to the signature scheme or signature encoding. The remediation was therefore relatively straightforward.
Remediation

We have fixed the reported issue by making following changes:

  • The dimension-two isogeny-chain computation now returns an explicit success or failure status.
  • Codomain data are produced and used only when the final splitting step succeeds.
  • The verifier checks the returned status and immediately rejects the signature if the computation fails.
  • Necessary basis-recovery and point-on-curve conditions are now enforced by unconditional runtime checks rather than debug-only assertions.
  • Malformed-input failure paths were revised so that verification never continues with incomplete intermediate values.
Outcome
After these changes, the verification result is determined solely by the public key, message, and signature. Valid signatures continue to verify correctly, while all-zero signatures, signatures for a different message, and malformed signatures that cause the isogeny-chain computation to fail are consistently rejected.

In progresssign-25-2: Isogeny prime sizing relies on the former square-root attack costDate not stated

This response concerns report sign-25-2: Isogeny prime sizing relies on the former square-root attack cost.

Confirmation
We confirm the reported issue.
Root cause
The original parameter sets were selected according to the previously accepted square-root attack complexity. In light of the newly published attack algorithm and the resulting security estimates, the sizes of the underlying primes need to be increased accordingly.
Scope
This is a parameter-selection issue and does not require a fundamental change to the signature scheme. The scheme uses primes of the form p = f · 2a · 3b − 1. There are sufficiently many primes of this form to satisfy the revised security requirements as well as the arithmetic and implementation requirements of SQIsign2D2. Therefore, generating and integrating larger parameter sets does not present any fundamental difficulty.
Planned changes

We are addressing the reported issue by making the following changes:

  • The prime sizes will be increased according to the complexity of the new attack algorithm.
  • New primes of the required form will be selected for the affected security levels.
  • The corresponding field arithmetic parameters, torsion parameters, precomputed constants, encodings, and test vectors will be updated consistently.
  • The revised parameter sets will undergo correctness, security, and performance validation.
Status
This work is currently in progress. The updated parameter sets and their supporting security analysis will be included in a subsequent release.

Fixedsign-25-3: Detached compact challenge enables one-query message-retargeting forgeriesDate not stated

This response concerns report sign-25-3: Detached compact challenge enables one-query message-retargeting forgeries.

Confirmation
We confirm the reported issue.
Root cause
In the original compact-signature implementation, the hash-derived challenge was transmitted and checked as a relatively independent signature field. However, the verifier did not sufficiently bind this value to the geometric relation between the reconstructed forward challenge isogeny and the encoded dual path. Consequently, the response and dual-path data could remain unchanged while the transmitted challenge was recomputed for a different message.
Scope
The remediation was conceptually clear, but it required coordinated changes to the compact signature format and to both signing and verification. It was therefore a moderate implementation change rather than a single additional input check.
Remediation

We have fixed the reported issue by making following changes:

  • The compact signature no longer carries the hash-derived challenge as a detached value.
  • During signing, the challenge kernel is constructed directly from the hash of the public key, message, and commitment curve using a canonical basis.
  • The compact encoding was updated to include the auxiliary information required to reconstruct the commitment curve and challenge relation during verification.
  • During verification, the commitment curve is reconstructed from the response and encoded dual-path information.
  • The verifier recomputes the challenge for the message being verified, constructs the corresponding forward challenge kernel, and checks that it is compatible with the recovered dual challenge path.
Outcome
These changes bind the message, commitment curve, forward challenge kernel, and dual challenge path within a single verification relation. Changing the message or replacing a challenge value without updating the associated geometric data no longer produces a valid signature.

Fixedsign-25-4: Noncanonical field encodings create signature and public-key aliasesDate not stated

This response concerns report sign-25-4: Noncanonical field encodings create signature and public-key aliases.

Confirmation
We confirm the reported issue.
Root cause
The issue was caused by the absence of complete canonical-encoding checks in the serialization and verification layers. Field elements were decoded without first checking that their integer encodings were strictly smaller than the field modulus p. Consequently, when x + p fitted within the encoded field width, the encodings of x and x + p were decoded as the same field element. In addition, the verification interface did not enforce the exact signature length, so appended bytes were ignored. For uncompressed signatures, the response matrices M and −M mod 2e represented the same underlying relation, but the encoding did not select a unique representative.
Scope
This was a localized encoding-validation issue and did not require any change to the underlying signature scheme. The remediation was relatively straightforward, although the changes had to be applied consistently to signing, encoding, decoding, and verification across all parameter sets and implementations.
Remediation

We have fixed the reported issue by making the following changes:

  • Every serialized base-field component in public keys and signatures is now checked before decoding, and encodings greater than or equal to p are rejected.
  • The verification interface now requires the public-key and signature lengths to be exactly equal to their specified encoded lengths. Truncated inputs and inputs containing appended bytes are rejected.
  • A canonical sign convention has been introduced for uncompressed response matrices. The entries are examined in row-major order, and the first odd entry is required to be smaller than 2e−1.
  • During signing, the implementation selects between M and −M mod 2e so that the encoded response matrix satisfies this convention. During verification, the noncanonical alternative is rejected.
  • The canonical-encoding checks are performed before deserialization and have been applied consistently to all Reference and Optimized parameter instances, in both compressed and uncompressed configurations.
Outcome
We tested all supported parameter sets and implementations. Valid public keys and signatures continue to be accepted, while field-element aliases obtained by adding p, signatures containing appended bytes, incorrect encoded lengths, and negated response-matrix aliases where applicable are consistently rejected.
